# ADR-014 — Travail et Services : la présentation non éditable reste dans le frontend, jamais en D1

**Décision.** Aucune colonne `layout`/`block_type` n'existe en D1, ni pour Travail (`work_items`) ni pour Services (`services`). D1 stocke uniquement le contenu (sélection, ordre, catégorie, textes, référence média). Le frontend calcule ou associe seul toute décision de présentation que l'admin n'a pas le droit de modifier :
- **Travail** : la composition (full/centered/large/offset/duo) est calculée par le frontend à partir de la position, du nombre total d'éléments et de la bande de ratio de chaque image.
- **Services** : les trois compositions (wide-offset/split/text-image) sont associées en code à l'identifiant stable `services.slug` de chaque service.

**Contexte.** `docs/DATA_ARCHITECTURE.md` (Brief 009) recommandait déjà l'Option 1 pour Travail (pas de colonne `layout`), mais proposait de conserver `layout` comme colonne réelle (non éditable) sur `services`, au motif que Services est un ensemble fixe à 3 éléments dont la variété visuelle est voulue par élément. La Review 009A tranche différemment pour Services : même conclusion que pour Travail, `layout` sort entièrement de D1.

**Pourquoi.** Principe produit « contenu ≠ design » (Master Brief 7.6) et Visual Editor Spec (« ce que l'admin ne peut pas faire : modifier la mise en page ») : une donnée que l'admin n'a explicitement pas le droit de changer n'a pas besoin de vivre dans la base de contenu, même si elle est techniquement structurée/typée. La garder en D1 sans l'exposer à l'édition n'apportait qu'un faux sentiment de « donnée pilotée », alors qu'elle ne peut en pratique être modifiée que par une migration — autant la garder où une telle modification a réellement lieu : le code. `slug`, lui, reste en D1 : c'est un identifiant de contenu stable et référencé (utilisé par le frontend pour retrouver le layout associé), pas une décision de présentation.

**Alternatives.** Garder `layout` en colonne D1 non éditable pour Services (proposition initiale du Brief 009 — écartée par cette révision, incohérence relevée avec le traitement de Travail). Exposer `layout` à l'édition dans le Visual Editor pour l'un ou l'autre (écarté — contredit directement Visual Editor Spec et le principe contenu ≠ design).

**Conséquences.** `services` n'a plus de colonne `layout` (retirée de `docs/drafts/001_initial.sql`). Toute page consommant `services` doit résoudre la présentation via une correspondance frontend `slug → layout` (par ex. un petit objet constant dans le code), à concevoir en Phase 5. Ce principe de séparation (D1 = contenu, frontend = présentation non éditable) s'applique par défaut à toute décision future du même type, pas seulement à Travail/Services — voir `docs/DATA_ARCHITECTURE.md`, « Séparation D1 / frontend — réaffirmée ».
