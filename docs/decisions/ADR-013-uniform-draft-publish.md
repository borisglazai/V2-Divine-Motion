# ADR-013 — Brouillon/publié : mécanisme unique pour tout contenu public éditable

**Décision.** *Save Draft ≠ Publish* s'applique sans exception à tout contenu public éditable — `work_items`, `services`, `testimonials`, et les 5 tables de contenu de page (`home_content`, `work_page_content`, `services_page_content`, `about_content`, `contact_content`). Chacune porte le même mécanisme : `status` (`'draft'` | `'published'`) et une auto-référence `draft_of_id`. La ligne `status = 'published'` est la seule que le site public lit ; au plus une ligne `status = 'draft'` peut exister par ligne publiée (index unique partiel sur `draft_of_id`). Modifier un élément déjà publié édite sa ligne brouillon, jamais la ligne publiée directement ; « Publier » copie les colonnes du brouillon sur la ligne publiée dans une transaction, puis supprime le brouillon.

**Contexte.** `docs/DATA_ARCHITECTURE.md` (Brief 009) proposait initialement un modèle hybride : statut simple sur la ligne pour `work_items`/`services`/`testimonials` (contenu jugé court et atomique), ligne brouillon séparée uniquement pour le contenu de page (scénario d'édition longue). La revue DATA ARCHITECTURE REVIEW 009A a explicitement rejeté cet hybride : la règle produit *Save Draft ≠ Publish* ne souffre aucune exception, quelle que soit la taille du contenu concerné.

**Pourquoi.** Un mécanisme unique, appliqué partout, est plus simple à comprendre, à tester et à maintenir qu'une règle qui varie selon le type de contenu — et élimine le risque qu'un admin découvre, par surprise, qu'éditer une légende `work_item` publie immédiatement sa modification alors qu'éditer un texte de page ne le fait pas. Réutiliser le mécanisme déjà conçu pour le contenu de page (plutôt qu'en inventer un second) coûte peu : quelques colonnes et un index par table supplémentaire.

**Alternatives.** Le modèle hybride initial (écarté par la Review 009A — voir Contexte). Une ligne brouillon complètement séparée dans une table dédiée par entité (écarté — multiplierait les tables sans bénéfice sur le mécanisme lui-même, qui reste identique). Un vrai système de révisions/versions (écarté — hors de portée du MVP, voir `docs/DATA_ARCHITECTURE.md` « Versioning / Rollback », couvert à la place par `content_snapshots`).

**Conséquences.** `work_items`/`services`/`testimonials` gagnent chacune `status` et `draft_of_id` (+ index unique partiel). Le réordonnancement en masse de `work_items` (glisser-déposer de plusieurs éléments) passe désormais, à la lettre, par plusieurs paires brouillon/publication — le schéma le permet nativement en une seule transaction applicative, mais l'ergonomie CMS exacte reste à concevoir en Phase 5 (voir `docs/DATA_ARCHITECTURE.md`, Risks). `content_snapshots` s'applique aux mêmes entités, pour un rollback cohérent avec cette extension. Voir `docs/drafts/001_initial.sql` pour l'implémentation et les tests associés.
